DAN: Right. Then the reader clicks unlock. The page builds a transaction: move this amount from the reader's wallet to the writer's wallet.

DAN: Then the transaction goes to the network, and a few seconds later it's confirmed.
SAM: Now here's the part that beginners often skip. The browser says: I paid, please unlock. Should the server believe it?
DAN: Never. The browser is not trustworthy. Anyone can send a request that says I paid.
SAM: So the server looks up the transaction on the blockchain itself. Does it exist? Did it succeed? Did it send enough money, from this reader, to this writer?
DAN: And one more check that's easy to forget: has this transaction been used before?
SAM: Oh, good point. Otherwise one payment could unlock every article on the site.
DAN: Exactly. So the server stores each transaction signature once, in a database. If it shows up again, it's rejected.
SAM: What kind of database do you need for that?
DAN: For a prototype, something small like SQLite is plenty. It's just a file on the server. You store users, articles and purchases.
SAM: Then there's the question of accounts. Why do you even need a login if you have a wallet?
DAN: Good question. A wallet address alone doesn't prove who is asking. If purchases were linked only to an address, someone could type in your address and read your articles.
SAM: So linking purchases to a logged-in account closes that gap. The login proves who you are, and the blockchain proves you paid.
DAN: And then there's the network. Everything we described runs on devnet, where test tokens are free.
